## 三个根因

### ① GPU 分配是静态的 → 两进程挤一张卡 → 级联 OOM
`run_eval_parallel.py::build_tasks` 用 `gpu = ENC_GPUS[wid % 6]` **硬映射**，
不看那张卡是否真的空。worker 早退（如 freechunker/code-repo 3 分钟就 OOM）
后，调度器把下一个 worker 派到「编号对应」的卡上，而那张卡上原来的 worker
**还在跑**。
- 实测证据：`eval_w07` 的报错里点名 `Process 1187668`（= w01），
  而 w07 自己被分到 GPU3 —— 与 w01 同卡。✅ 铁证
- 每个 eval worker 实际吃 **10–20 GB** 显存（我原以为 1.5 GB），
  所以一张 24 GB 卡**只能放一个 worker**。

### ② vLLM 上下文不匹配 → HTTP 400 整域归零
- 评测侧：`test_*.py` 里 `self.max_context_length = 40000`（截到 ~39k token）
- vLLM 侧：`start_vllm.sh --max-model-len 16384`
→ 超长 prompt 被拒：`You passed 15873 input tokens and requested 512 output
  tokens. However, the model's context length is only 16384`
- 命中：w23(margin/long-structured)、w27(semantic/long-dialogue) 整域归零
- **实测 vLLM 上限**：`max_model_len=40960` 起不来，报
  `estimated maximum model length is 36160`（gmu=0.92）
- Qwen3-8B 原生上下文 = **32768** → 应设 32768

### ③ FreeChunker 在大上下文域**硬 OOM**（无解，需决策）
`test/test_freechunker.py:160` 把**整个原始 context** 喂给
`build_vector_store(context)`，**无截断、无窗口**：
```
context = sample['context']              # 全文，最大 16M 字符
self.encoder.build_vector_store(context) # → src/encoder.py:83
  outputs = self.model(inputs_embeds=inputs_embeds)   # [1, N_sentences, 1024]
```
FreeChunker 模型对**全部句子**做一次注意力 → O(N²)。
code-repo 句子数中位 **37,458**、最大 403,011
→ 37k² × 16 heads × 4B ≈ **87 GB**，24 GB 卡无解。
- 实测 w02: `Tried to allocate 23.65 GiB`（单次分配就超卡容量）
- → **code-repo(50) 与 long-structured(33) 完全没有 FreeChunker 数据**，
  而它是主角方法。这是 3090 复现的硬约束，不是 bug。
- 官方仓库就是本项目，即官方评测代码本身没有上下文上限
  → 论文应该是在更大显存的卡上跑的。

## 第二次失败复盘（10:20 小布发现「卡4,6,7 好像是空的」）

### 现象
重跑 27 分钟后：ppl 6/6、lumber 6/6、margin 5/6、semantic 5/6 全部 `raw=0`，
`fail=2`；只有 freechunker 6/6 全绿。

### 关键区分：**不是挤卡了**
报错里**没有别人的 pid**（动态取卡生效了）：
```
Tried to allocate 8.00 GiB. GPU 0 has ... 4.85 GiB free.
this process has 18.70 GiB memory in use. 18.38 GiB is allocated by PyTorch
```
「this process has 18.70 GiB」= 整张卡的占用**都是它自己**。
→ 是**单进程自己超过 24 GB**，跟上一个 bug 完全无关。

### 根因：embedding 阶段的 batch_size × 长 chunk
堆栈指到：
```
test_ppl.py:173  chunk_embeddings = self.embedding_model.encode(chunks)
test_ppl.py:38   → SentenceTransformer.encode(batch_size=<包装类默认>)
```
各包装类默认：ppl=4, traditional/lumber/semantic=6, margin=4。

`SentenceTransformer.encode` 会把一个 batch pad 到**该 batch 最长**的那条，
注意力矩阵 = `batch × heads × L²`。jina 的 max_seq_length=8192，于是：

    batch=4 × 8 heads × 8192² × 4B ≈ **8.6 GB**  ← 与报错 "Tried to allocate 8.00 GiB" 吻合
    batch=6 × 8 heads × 8192² × 4B ≈ **12.9 GB**

**实测显存轨迹**（ppl × single-doc，limit=60，每 12s 采样）：
```
2753 → 3809 → 3809 → 3809 → 10013 → 17111 → 17111 ×4 → 15579 → OOM(42/60)
```
**阶梯式跳升**，每次跳升 = 一个「长 chunk 扎堆」的 batch。

### 附带测到的 chunk 长度分布（解释为什么是这几个方法挂）
| 方法/域 | chunk 数中位 | 最长 chunk |
|---|---|---|
| Lumber/code-repo | 1,619,616 | **15,185,774** |
| Lumber/long-structured | 550,920 | 9,781,859 |
| Semantic/code-repo | 91,168 | 3,542,992 |
| PPL/code-repo | 14,358 | 282,864 |
| Traditional/256/* | 1k–1.8k | ≤ 14,023 |
| Margin/* | 1.5k–10k | ≤ 840,733 |

Lumber/Semantic 的 chunk 动辄**上百万字符** → batch 里全是 8192-token 的长文本
→ 必爆。Traditional 的 chunk 是定长 256/512 token，所以它基本能跑通。

### 修法
`setup/patch_embed_batch.py`：5 个 `test_*.py` 的包装类
```python
def encode(self, texts, batch_size=None):
    if batch_size is None:
        batch_size = int(os.environ.get('FC_EMB_BATCH', '1'))
```
默认降到 **1**（batch=1 → 8 × 8192² × 4 ≈ 2.1 GB）。
另外在评测环境加 `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`。

代价：embedding 变慢。但它只占每题 3–5 s 的一部分，换来不再整域归零。

### 验证（两个场景都过）
| 场景 | 修前 | 修后 |
|---|---|---|
| ppl × single-doc（limit 60）| 17111 MiB → **OOM @42/60** | 峰值 8885 MiB，**跑到 58/60 无错** ✅ |
| lumber × code-repo（limit 5，chunk 中位 161 万字符）| 必 OOM | 峰值 8905 MiB，产出 10 行 raw ✅ |

### 教训
**「修好一个 bug」不等于「问题解决」。** 第一轮我修了挤卡，第二轮暴露了
单进程超限 —— 两者都会表现为同一个 `CUDA out of memory`，
**区分方法只有一个：看报错里有没有别人的 pid。**
没有 → 单进程自己超限，要查它自己在算什么。

## ⚠️ 更正（12:35）—— 上一条「granularity 不一致」的结论是**错的**
