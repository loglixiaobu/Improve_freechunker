## 关键结论（后续接着做时直接看这里）

### 项目结构
- `src/`：encoder(UnifiedEncoder) / freechunker(FreeChunkerModel) / sentenizer / aggregator / configuration / utils
- `test/test_freechunker.py` 是主评估入口；`test/test_{Traditional,Semantic,ppl,margin,lumber}.py` 是基线
- `train and preprocess/1_build_pretrain_datasets.py` 造训练数据；`3_train_jina.py` 训 jina
- 仓库**没有** `upload_prep/`（README 提到了但不存在）

### 目标模型 jina-embeddings-v2-small-en 的复现要点
- 训练数据 `XiaSheng/FreeChunk-corpus`（HF，3.6GB）：train 7 shards × 14,286 = **100,000 篇**，
  字段 uuid/sentences/source/original_token_count，每篇恒 8000 token，`sentences` 平均 **124.1 句**
- 官方训练 **200,000 步** = 2 epoch × 100k × batch 1；官方 `training_losses.json` 可当验收靶子
  （前 1000 步均值 0.4497，final_val **0.0103**，后段稳在 0.0103）
- 编码量：granularities [2,4] → 每篇 mean 184.5 span + 124.1 句 = **308.6 条**；全量 **30.9M** 条
- 实测 jina-small 在 3090 上 **832 texts/s**（bs=32，峰值显存 2.53GB，dim=512）
  → 单卡 10.3h，8 卡分片 ~1.3h；**训练反而单卡够**（~5h）
- 向量落盘 ≈ **63GB**

### 论文 vs 代码（重要，别按论文改代码）
1. 论文说训练 5 个粒度 (2,4,8,16,32)；**代码默认 [2,4]**，官方 config `max_power: 4`
2. 论文说 Sentenizer 与传统分块同规则（256 token）；**训练语料里是真句子（≈64 token/句）**，
   推理侧代码才产出 256-token 块 —— 训练/推理粒度本来就不一致
3. 论文说 Traditional 基线「按句号切分再累积」；**代码是纯 token 滑窗截断**
4. 三个 backbone 训练脚本**都** `from_pretrained('BAAI/bge-m3')` —— **不是 bug**，
   论文 §4.2 自称「fixed 330M-parameter sentence-level encoder for all three」
   → 跨粒度编码器 = XLM-R-large 几何（24 层/hidden 1024/16 头/4096/`vocab_size=2`）≈302–330M

### 阻断级坑（执行时必须先修）
1. `1_build_pretrain_datasets.py` 存 `vector/jina-.../part_N`，`3_train_jina.py` 读
   `vector/jina-.../train` —— **路径不匹配**，必须补合并步骤

   `/share/home/ecnuzwx/UnifiedRAG/cache/models--Qwen--Qwen3-8B` → 服务器上不存在，
   且它决定句子切分粒度，直接影响结果

   → 必须自己按 `domain` 字段拆成 6 个子目录 + `dataset_dict.json`
   （domain 全名 → 目录名：`Single-Document QA`→single-doc、`Multi-Document QA`→multi-doc、
   `Code Repository Understanding`→code-repo、`Long In-context Learning`→long-icl、

## 三个真 bug（都靠冒烟测出来的，没上生产）

1. **`Features` 少一层** → `TypeError: Couldn't cast array of type list<item: float> to float`。
   一行值是 `[n,512]` 二维表，必须是 `Sequence(Sequence(Value("float32")))`。
   原始仓库压根不 cast（`Dataset.from_list` 从 float32 numpy 推断出来就是对的）。
2. **固定 batch_size 撞长尾 → 8 分片集体 CUDA OOM**。
   量出来的分布：句子 token p50=48 / p99=302 / p999=817 / **max=3471**；
   chunk token p50=136 / p99=692 / p999=1595 / **max=7078**。
   注意力 `B*H*L^2*4`，B=32、H=8、L=7078 → **51 GB**。
   → 改成按长度分桶（`B*Lmax² ≤ 8e7`）+ OOM 二分重试。
   **原仓库 batch_size=8 不是偷懒，是这条长尾的边界。**
3. **`ds[i]` 慢到占整步 34%**：默认格式把 Arrow 转 Python 嵌套列表，**61.9 ms/步**；
   `.with_format("numpy")` → **2.5 ms**（25×）。180 → 145 ms/step，20 万步省 **3.3h**。
   loss 数值逐位不变（脚本里有自检断言）。

## 踩到的新坑（重要）

1. ⚠️⚠️ **服务器上裸 `python` 是 Python 2.7.18！**（`/usr/bin/python`）
   所有 `python -m py_compile` / `python -c "..."` 检查都会报假 SyntaxError。
   **必须先 `source ~/miniconda/etc/profile.d/conda.sh && conda activate freechunker`**（那个是 3.10.22）。
   我在这上面浪费了 3 次往返，还一度以为是文件坏了。
2. `sed -i "s/\r$//"` 在**双引号 shell 串里**会把 `\r` 解释坏 → 用 `tr -d "\r" < f > t && mv t f`。
3. 在**登录 shell 的 heredoc**（`python - <<EOF`）里写中文 → Python 2 报 `Non-ASCII character`。
   一律写成本地文件再上传。
4. **`pkill -f "chunk_xxx"` 会杀掉自己的 ssh shell**（Exit 255）。
   改成 `ps -eo pid,cmd | grep "[c]hunk_xxx" | awk '{print $1}' | while read p; do kill -9 $p; done`。
5. **本地 Bash 工具约 120s 超时**，`sleep 150; ssh ...` 组合会被 SIGTERM。
   `sleep` 要单独发，ssh 查询另发。
