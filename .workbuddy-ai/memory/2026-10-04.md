# 2026-10-04 · FreeChunker 下游评测（多卡并行）

## 大思路（小布的两条指令）

1. 「**为什么不多卡并行跑呢，2-7 的 gpu 都是空的**」
2. 「**一张卡跑一个任务/数据集（只要不 oom）**」

→ 整个下游 chunking + 评测全部改成**进程级并行**。

## 这一天真正解决的问题

### ① 评测入口 `_apply_keep` 的 `KeyError: 'chunks'`（根因 + 修复）

**症状**：`test/test_Traditional.py:164  chunks = sample['chunks']` → `KeyError: 'chunks'`

**根因**：`test/eval_downstream.py` 的 `_apply_keep` 写死了从 `split_by_domain` 读数据，
但那份**原始 LongBench 没有 `chunks` 字段**。5 个 baseline 必须读**各自的 chunked 目录**
（`LongBench-v2_chunked/<Method>/<model>/`）才有 `chunks`。

**修复**：`_apply_keep(qa, ...)` 优先用 **QASystem 自己加载的那份**（`getattr(qa, "datasets")`），
只有 FreeChunker（走 `split_by_domain`、靠 encoder 现场分块）才回退。

⚠️ **我踩的坑**：修完本地没上传，白跑一次冒烟。教训 —— **改完立刻 `tar czf - <file> | ssh ... tar xzf -`，再 grep 校验落地**。

**验证**：traditional → `EVAL_DONE` 33.33%(1/3)，2.43s/题；freechunker → `EVAL_DONE`，3.61s/题。

### ② Lumber 慢到不可接受（真因不是「模型慢」，是**并发度太低**）

**第一直觉错了**：以为 Lumber 是「一个样本 116 次串行 vLLM 调用」所以必然慢。

**实测数据推翻了这个判断**：

| 并发数 | 吞吐 | 单次延迟 |
|---|---|---|
| 8 | 2.1 req/s | 3.7s |
| 16 | 4.6 req/s | 3.5s |
| 32 | 8.7 req/s | 3.6s |
| 48 | 15.5 req/s | 2.9s |
| 64 | 12.5 req/s | 5.0s |
| 96 | **25.7 req/s** | 3.5s |

→ **vLLM 并发几乎线性扩展**，而之前只有 6 个 worker ⇒ 只有 0~1 个请求在飞。

**Lumber 单次调用其实很便宜**：`max_tokens=100` + `chat_template_kwargs={"enable_thinking": False}`
→ 只出 **6 个 completion token**，0.44~0.8s 一次。算法是 O(n) 次调用/文档（每约 550 词推进一次）。

**正确修法**：把 worker 从 6 加到 **48**（纯 HTTP 客户端，不占显存，503G 内存随便开）。
实测并发请求数从 0~1 涨到 **~38**（8888=19, 8889=19），
进度从 ~25 样本/小时 变成 **~3 样本/分钟**（300 样本 → 约 90 分钟，原来要 12h+）。

⚠️ **补丁脚本自身的两个 bug（都是「raw string 忘了 .format()」）**：
- `{marker}` 占位符没替换 → `NameError: name 'marker' is not defined`
- `{{}}` 双重花括号没还原成 `{}` → `TypeError: unhashable type: 'dict'`
**教训**：用 `.format()` 的模板字符串，写完必须**真跑一次**，不能只 `py_compile`（语法过≠逻辑对）。

### ③ Lumber 全局完成池（worker 数可随意变）

原来 checkpoint 是**每 shard 一个文件**，worker 只读自己那份 → 改 worker 数（6→48）后
`i % nshards` 映射全变，老 checkpoint 对不上，会重跑。

**修法**：新增 `checkpoints/_done_global.jsonl`（append-only 全局池），
启动时并入 `processed_samples`，实现**跨 shard 断点续跑**。
配 `setup/build_lumber_done_pool.py` 把历史 shard 文件灌进池。

### ④ PPL / Margin 打「按域分片 + 逐样本 checkpoint」补丁

**问题**：
- PPL 是**整批一次性 `save_to_disk`**（中途崩 = 全丢），Margin 是逐域保存（好一点但仍无中途续跑）
- 两者都**没有分片能力**，只能单卡串行

**补丁 `setup/patch_cm_shard.py`** 统一加：
- `FC_CM_DOMAINS` / `FC_CM_SHARD` / `FC_CM_NSHARDS` 按域分片
- 逐样本 append JSONL 到 `checkpoints/<domain><.shardN>.jsonl`，按 `_id` 去重续跑
- 输出目录带 `.shardN` 后缀 + `dataset_dict.shardN.json`（PPL 顺带改成逐域保存）
- 配 `setup/run_cm_parallel.py`（多卡启动器）+ `setup/merge_cm_shards.py`（合并）

**实测**：PPL 在 GPU7 跑通，schema 正确（`chunks` 有 199 条），**59.1s/样本**（long-structured）。

## 关键认知：Lumber 是「纯 HTTP 客户端」

这是 6 个 chunker 里**唯一不占 GPU** 的，也是能开 48 worker 的原因：

- PPL / Margin / Semantic：模型 `model.to('cuda:N')` **加载进本进程** → 常驻 15~24GB 显存
  → **一个进程必须独占一张卡**（硬约束）
- Lumber：模型在 vLLM（GPU0:8888 / GPU1:8889）里，chunker 只是 `OpenAI(base_url=...)` 客户端
  → 自身显存 **0 MiB**，启动器给它设 `CUDA_VISIBLE_DEVICES=`（空）
  → **能开任意多个 worker 并发压 vLLM**

**推论**：Lumber 的算力上限 = 那 2 个 vLLM 实例（GPU0/1），**加 worker 有用、加卡没用**；
而 PPL/Margin/Semantic 是「一卡一进程」，**加卡就能加吞吐**。两类 chunker 的本质差异。

## 15:30 更新 · 三个真 bug + Lumber 补齐 4 域

### ⚠️ 我犯的三个错（小布点出来才发现的）

小布说：「**不用着急跑，卡不够就先不跑别的，时间不着急，这样跑的话，等下都出错了，还不知道哪里错误了**」
—— 这是对的。我当时 `rebal` 一出错就手动补 6 个进程、手劈 multi-doc、还把
专职看护的 `rebal` 会话杀了，**没有任何东西在看护**。3 个真 bug 是这么暴露的：

#### Bug 1（严重）：`rebalance_ppl.py` 的 `export` 只作用于第一个变量

```python
env = (...
  f"export FC_CM_DOMAINS={dn} && FC_CM_SHARD={shard} FC_CM_NSHARDS={nshards} && ")
```
`export A=1 && B=2 C=3` 里 **export 只管 A**；`B=2 C=3` 是普通 shell 变量，
而 `VAR=v cmd` 这种前缀赋值作用在紧跟的 `cd` 上，**不会进 python 环境**。

**症状**：三个 multi-doc 分片日志全是 `[cm] shard=0/1`（默认值），
**三进程重复算同一批 19 个样本**，新增 = 0。

**修法**：每个都单独 `export`。（已改 `setup/rebalance_ppl.py`）

#### Bug 2（设计缺陷）：按「域」切片切不开单域

```python
picked = [d for d in picked if d in _CM_DOMAINS]
picked = picked[_CM_SHARD::_CM_NSHARDS]   # ← 单域时只有 shard0 拿得到
```
`['multi-doc'][1::3] = []` → shard1/shard2 拿空域，直接空转。

**修法**：分片维度改成**样本索引**。新增 `_cm_keep_idx(n)` 返回
`set(range(shard, n, nshards))`，在**各域内部**挑样本。
已写成 `setup/patch_ppl_sample_shard.py`（离线验证过：42/42/41 互补无重叠）。

### ② PPL 为什么占 15.8 GiB（实测 + 精算）

**权重只有 2.88 GiB。** 其余 ~13 GiB 全是中间激活，三杀手叠加：

| seq | `logits` | `shift_logits` 副本 | attn 矩阵 | KV cache | 合计 |
|---|---|---|---|---|---|
| 8192 | 2.32 | 2.32 | 1.50 | 0.22 | **9.2** |
| 16384 | 4.64 | 4.64 | 6.00 | 0.44 | **18.6** |
| 32768 | 9.27 | 9.27 | 24.00 | 0.88 | **46.3** |

(GiB，Qwen2-1.5B: h=1536 L=28 kv=2 hd=128 V=151936)

1. `logits` 形状 `[1, S, 151936]` —— **vocab 15 万**，S 稍大就胖；
   `get_ppl_batch` 里 `.contiguous()` **再复制一份** → 双倍。
2. **attention 是 O(S²)**，且本机 `flash_attn` **没装**
   （`is_flash_attn_2_available: False`）→ 只能 eager，S×S 矩阵实打实落显存。
3. `use_cache=True` + `return_kv=True` KV 全程不释放（但只 0.88 GiB，非主因）。

**context 长度实测**（tokenize 真实值，注意 `length` 字段是 `"long"` 标签不是数值）：

| 域 | min | med | max |
|---|---|---|---|
| long-dialogue | 24K | 43K | 120K |
| single-doc | 24K | 139K | 323K |
| long-icl | 97K | 182K | **147万** |
| long-structured | 58K | 212K | 515K |
| multi-doc | 48K | 234K | 521K |
| code-repo | 77K | 441K | **117万** |

PPL 是**整篇一次前向**算逐句 loss 曲线，必须全序列 → 实际被
`max_position_embeddings=32768` 钳住（日志有 `... (69213 > 32768)`），落在 16K~32K。

**可优化点**（未做，需小布同意）：`num_logits_to_keep=1` 或只要 loss 不留全 logits，
S=16384 时能从 18.6 压到 ~8 GiB，一卡能塞两个。

## 17:30 更新 — ⚠️ 我误杀了两个 worker + 长尾域分片重铺

### ❌ 重大失误：`tmux kill-session -t mgshort` 连带杀死子进程

**发生了什么**：上一步我清理空转会话时执行了
`for s in vllm vllm1 lmb mgshort sup semp; do tmux kill-session -t $s; done`

其中 **`mgshort` 是 Margin 短域 supervisor**。而 `run_margin_short.py` 是用
`subprocess.Popen(["bash","-c",cmd])` 起 worker 的 —— **worker 是 supervisor 的
子进程**，不是独立 tmux 会话。杀 supervisor = 杀它整个进程组。

**代价**：正在跑的
- `long-dialogue` 38/39（差 1 条）
- `long-icl` 7/81（差 74 条）

**误判过程**：我先看到 GPU3/7 空了、进程没了，第一反应是「跑完了」，
差点就这样报给用户。是**日志里没有 `EXIT=` 标记**（wrapper 退出必写）
+ **日志 mtime 停在 17:18** 让我起了疑，才追到真相。

**根因**：**假设了 worker 在独立 tmux 会话里，实际是 Popen 子进程。**
（对比：`run_margin_rest.py` 我写的是 `tmux new-session -d` —— 那个是独立的，
所以它的 3 个 worker 活下来了。两个脚本风格不一致，我没注意。）

**损失可控**：checkpoint + `_id` resume 让重跑无损。38 条、7 条都还在盘上。

→ **修正**：新脚本 `setup/shard_margin_longtail.py` 一律用
`tmux new-session -d -s <唯一名>` 起 worker，与会话无父子关系。

### 教训（写进 skill）
1. **杀 supervisor 前先确认 worker 是「子进程」还是「独立会话」。**
   `Popen` → 同生共死；`tmux new-session -d` → 独立。

2. **进程消失 ≠ 任务完成。** 判完成永远看产物 + 是否有退出标记（`EXIT=`）。
   这次就是「没 EXIT 标记 + mtime 停滞」两个信号救了我。
3. **同一天写两个功能的脚本，起进程的方式要保持一致**，否则一个的清理逻辑
   会误伤另一个。

## 23:00 更新 — 查清「GPU7 为什么还没跑完」

小布问「GPU7 这个还没跑完？」。**没卡死，是真在算**，但我的代价模型一开始选错了。

### 证据（三查）
- `State=R`，CPU ticks 持续增长（485354→491381→495354）
- GPU7 利用率 74–100%，显存 18 GB
- 日志 90 秒零增长 —— **但这是设计使然**：`llm_chunker_ms`
  （`lmchunker/modules/margin_sampling_chunking.py:136`）**每个文档只在结束时打印一次**
  `The program execution time is: ...`。所以处理大文档 = 长时间静默。

### ❌ 我先用了错的代价代理（两次）
| 代理 | 结论 | 为什么错 |
|---|---|---|
| **字符数** | 5 组差异 <2%，看着很均衡 | 字符 ≠ 工作量 |
| **段数** | 组504 段数最少(327k) 却最慢 | 段数也不对 |
| **Σ(段对长度)²** ✅ | 与实测耗时吻合 | 见下 |

根因：margin 的 `get_prob_subtract(sentence1, sentence2)` 是**逐「相邻段对」调模型**，
而且模型用 `use_cache=False` 加载 → 每次前向都要**重算全注意力**，
单次代价 ≈ O(L_pair²)。所以真实代价是 **Σ(段对长度)²**。

### ✅ 用 ΣL² 反推（可信 ETA）
| idx | 段数 | Σ(段对长度)² |
|---|---|---|
| 34 | 169,142 | 1,762,653,300 |
| 42 | 8,712 | 143,608,424 |
| 46 | 23,800 | 390,220,246 |
| **48** | **129,133** | **3,475,050,784** ← 是前三条之和的 **1.51 倍** |

`34+42+46` 实测 50 min，ΣL²=2.296e9 → 速率 45.9e6/min
→ index 48 需 **≈76 min**（22:26 起算）→ **约 23:42 完成**。
