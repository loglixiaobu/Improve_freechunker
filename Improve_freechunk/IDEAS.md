# 候选改进模块清单

按「预期收益 / 实现成本」排序。每个条目写清：**假设 → 为什么可能成立 → 改哪里 → 怎么验 → 预期 → 风险**。

判定门槛见 `README.md` 第三节（Overall ≥ +0.5pt 且 ≥4/6 域不变差）。

---

## 第 0 批：先对齐基线（不是改进，是修偏差）

### W1 · 句子窗口偏差

**假设**：`FC_MAX_SENTENCES=4000` 的窗口补丁在长文档上切断了跨窗口 chunk，
压低了 long-structured / long-icl 的分数（这两个域与论文差距最大：−12.1 / −6.2）。

**为什么可能成立**：
- 已验证 N ≤ 4000 时输出与**原实现逐位一致**，所以只有 N > 4000 的样本受影响
- 受影响样本的窗口边界处无法形成 chunk，等于丢失了部分候选
- 而差距最大的正是上下文最长的两个域

**改哪里**：`src/encoder.py::encode` 的窗口循环。

**怎么验**（CPU 即可，不需要 GPU）：
```python
# 用真实 splitter 统计各域句子数分布
from src.sentenizer import Sentenceizer
s = Sentenceizer(model_name='jinaai/jina-embeddings-v2-small-en')
for dn in DOMAINS:
    ns = [len(s.split(ds[i]['context'])) for i in range(len(ds))]
    print(dn, '中位', median(ns), '>4000 的条数', sum(1 for x in ns if x > 4000))
```
**判据**：若 >4000 的样本数很少（比如 <10 条），则窗口偏差**不足以解释** −12pt，
需要另找原因；若很多，则先修窗口再谈改进。

**预期**：先诊断，不预设结论。

### W2 · vLLM 上下文上限

**假设**：评测侧 `FC_EVAL_MAX_CONTEXT=32768`（原代码 40000）系统性压低长上下文域。

**为什么可能成立**：long-structured / long-icl 的检索结果最容易撞到上限被截断。

**怎么验**：统计有多少题的 prompt 被 `truncate_retrieved_context` 截断过
（代码里有 `⚠️ Retrieved context too long` 的打印，数一下日志即可）。

**判据**：若截断率 <1%，可排除；若 >10%，需要把 vLLM 上限提到 40000
（Qwen3-8B 原生 32768，超出部分要么接受质量退化，要么开 YaRN）。

## 第 1 批：纯检索层（不改模型、不需重训）

### I1 · 粒度感知的分数归一化 ⭐ 先做这个

**假设**：不同粒度的余弦相似度**分布不同**（长 chunk 的分数普遍偏高/偏低），
现在把所有候选**混在一起按原始余弦排序**，等于让某个粒度系统性挤占 top-k。

**为什么可能成立**：
- 长文本与查询的余弦相似度天然更"平滑"（接近均值），短句更"尖锐"
- 当前 `query()` 直接 `np.dot` 后 `argsort`，没有任何按粒度的校准
- 论文把 (1,2,4) 三档候选放进同一个索引，却没提分数校准 —— 这是一个明显的缺口

**改哪里**：`src/encoder.py::query`（或加一个后处理层），在排序前对每个粒度做
z-score 或分位数归一化。需要给 `vector_store` 加一个 `granularity` 标签数组
（可从 `grouped_texts` 的长度分布或 `grouped_sentences` 的长度反推）。

**怎么验**：固定 top-k，只改归一化方式，对比 Overall 与分域。

**预期**：Top-5 有提升空间（Top-10 因为候选多、被稀释，提升可能较小）。

**风险**：低。纯后处理，可开关，失败就回退。

---

### I2 · 混合检索（BM25 + 稠密，RRF 融合）

**假设**：code-repo 与 long-structured 依赖**精确匹配**（标识符、数字、键名），
稠密向量在这些场景天然吃亏。

**为什么可能成立**：这两个域的语料特征就是「查一个具体的符号/字段」。
本次实测 FreeChunker 在 code-repo 上 48.0%（已是最高的域），说明它不算差，
但 Traditional 只有 44%，且论文里 Lumber 在 code-repo 上 Top-10 达 52.67% —— 有空间。

**改哪里**：检索层加一路 BM25（`rank_bm25` 或 `bm25s`），
用 RRF（Reciprocal Rank Fusion）融合两路排名：
`score = Σ 1/(k + rank_i)`，k 常取 60。

**怎么验**：对比纯稠密 vs 融合，看 code-repo / long-structured 的变化。

**预期**：code-repo、long-structured 提升明显；single-doc / long-dialogue 基本不变。

**风险**：低（不改模型）。注意 BM25 需要中文/代码分词策略，英文代码可直接按 token 切。

---

### I3 · token 预算下的覆盖优化

**假设**：现在是「按分数取 top-k」，但不同候选**长度差异巨大**（1 句 vs 4 句）。
在同样的 token 预算下，应该选「覆盖信息更多、冗余更少」的组合，而不是分数最高的 k 个。

**为什么可能成立**：
- 论文的 `[Begin-t]/[End-t]` 机制本来就支持精确计算「候选集合覆盖了哪些句子」
- 当前 top-k 很可能选到多个高度重叠的候选 → 去重后实际覆盖很少
- 这是把「背包/最大覆盖」引入检索的经典做法

**改哪里**：`src/aggregator.py` 的选取逻辑 + 一个预算参数。
目标函数：`max Σ score_i`，约束 `Σ tokens_i ≤ budget`，且惩罚与已选集合的句子重叠。

**怎么验**：固定 budget（比如与 top-10 平均 token 数对齐），对比准确率。

**预期**：在 token 受限场景下提升明显；不限预算时提升有限。

**风险**：中（贪心实现要小心，别把简单问题做复杂）。

---

### I4 · 候选剪枝

**假设**：相邻候选 50% 重叠（`step_size = g//2`），向量库里存在大量冗余，可安全剪枝。

**为什么可能成立**：候选数随 n 线性增长（g=2 时 n-1 个，g=4 时约 n/2 个），
但对检索有用的候选远少于全部。

**改哪里**：`generate_shifted_matrix` 的步长；或检索时的候选过滤。

**怎么验**：对比不同剪枝率下的 准确率 / 向量库条数 / 检索耗时。

**预期**：向量库条数降 30–50%，准确率降 <0.5pt。

**风险**：低，但属于**开销方向**的改进，判定门槛不同（见 README）。

## 第 2 批：引入额外组件

### I5 · 重排（rerank）

**假设**：双塔（bi-encoder）召回 + cross-encoder 重排是成熟的两阶段范式，
FreeChunker 只用了第一阶段。

**改哪里**：召回 top-50 → 用 cross-encoder（如 `bge-reranker-base`）对
「query, 候选文本」打分 → 取 top-k。

**怎么验**：对比 rerank 前后的 Top-5 / Top-10。

**预期**：Top-5 提升通常最明显（rerank 擅长精排）。

**风险**：中 —— **会显著增加延迟**，与 FreeChunker 的"效率优势"叙事冲突。
必须在报告里同时给出耗时增量。

---

### I6 · 查询扩展

**假设**：单条查询对多跳/多文档问题覆盖不足。

**改哪里**：用 Qwen3-8B 把问题改写成 2–3 个子查询，各自检索后按 RRF 融合。

**预期**：multi-doc / long-icl 受益。

**风险**：中 —— 增加 LLM 调用（延迟），且改写质量不稳定。

---

### I7 · 粒度组合搜索

**假设**：论文只试了 (1,2,4)。更长文档可能需要更大的粒度档位。

**为什么可能成立**：论文自己说 (2,4,8,16,32) 是 Appendix D 的附加分析，
说明作者也认为粒度组合是可调的。

**改哪里**：`generate_shifted_matrix` 的 `granularities` 参数 + 重训（若要加新档）。

**怎么验**：先做**免重训**的版本 —— 只用已训练的档位 (2,4)，
额外把 g=8 也接进来（模型没训过 g=8，但可以试），对比效果；
若无效再考虑重训。

**预期**：long-structured / long-icl 受益。

**风险**：高（要重训 = 500 GPU 小时量级）；先做免重训的近似验证。

---

## 第 3 批：改模型 / 重训

### I8 · 对比学习训练信号

**假设**：现在是**余弦蒸馏**（拟合真值向量 `e`），
但下游任务是**检索排序**。拟合向量 ≠ 排序正确。

**改哪里**：在余弦损失外加 InfoNCE / hard-negative 项，
负样本用「同文档内不重叠的其他候选」+「其他文档的候选」。

**预期**：理论上限更高，但训练成本大、见效慢。

**风险**：高。

---

### I9 · 句子编码器微调

**假设**：Sentenizer 用的是**原始** jina-small，没有针对检索任务适配。

**风险**：高 —— 会破坏「与论文可比」的前提（论文用的是原始模型）。
**除非前面的都试过了，否则不建议动这条。**

---

## 排期建议

```
W1 诊断 ──► I1 归一化 ──► I2 混合检索 ──► I4 剪枝 ──► I3 预算优化
                                              │
                                              └──► I5 rerank（若要冲 Top-5）
                                                    │
                                                    └──► I7 粒度（需重训，最后）
```

**理由**：W1 决定基线可不可信（必须先做）；
I1/I2/I4 都是纯检索层、可开关、失败可回退，风险最低；
I5/I6 引入延迟，需要权衡；I7/I8/I9 成本最高，放在最后。
