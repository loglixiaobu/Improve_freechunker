1论文与代码理解

1.1 方法：句子为原子单位，一次前向出多粒度

文档 D │ ├─ Stage 1 Sentenizer D → S = {s₁..sₙ} → base 模型编码 → E ∈ ℝn×d │ ├─ Stage 2 Cross-Granularity Encoder │ Chunk Pattern Mask P ∈ {0,−∞}m×n P[i,j]=0 ⇔ 句子 j 属于第 i 个 pattern │ Q = W_Q·H（H = h_chk 复制 m 份，h_chk 可学习） K = W_K·E V = W_V·E │ Attn = softmax(QKᵀ/√d + P)·V → 24 层 XLM-R → 全部 m 个 chunk 表征（一次前向） │ ├─ Stage 3 Dense Retrieval embedding = [句子嵌入(粒度1); chunk 嵌入] 拼接 + L2 归一化 │ └─ Stage 4 Deduplicate & Concatenate 句子全局编号存为 【Begin-t】S_t【End-t】 top-k 候选按全局句序去重（同 index 留最高分），不连续处插 "..."

核心卖点：句子嵌入只算一次、被所有粒度复用；不做语义边界检测 → 比 LumberChunker / SemanticChunker 快 1–2 个数量级（论文 Fig.4 最高 30×）。

1.2 训练目标与超参

项值
监督形式蒸馏 —— teacher e = base 模型直接编码拼接句子；student v = FreeChunker 组合输出
LossL = 1 − mean(cos(e, v))（等价 nn.CosineEmbeddingLoss）
优化器 / lrAdamW / 1e-4，cosine decay + 前 1/3 步 warmup
batch / epochs1 / 2
验证每 1000 步，200 条样本
训练粒度代码默认 [2, 4]
推理粒度(1, 2, 4) —— 1 即原始句子嵌入，由 encoder 拼接实现
编码器规模XLM-R-large 几何：24 层 / hidden 1024 / 16 头 / intermediate 4096 / vocab_size=2 ≈ 302–330M

1.4 论文 vs 代码的 4 处不一致 复现必读

#论文写的代码实际处理方式
1训练对覆盖 5 个粒度 (2,4,8,16,32)generate_shifted_matrix 默认 [2,4]；官方 config.json 里 max_power: 4按代码 [2,4]。官方 loss 曲线就是 [2,4] 训出来的，改成 5 个粒度反而对不上
2Sentenizer 用「与传统分块相同的切分规则」（256 token）语料 sentences 平均 124 句/篇（≈64 token/句）是真句子；而推理侧 TraditionalChunking(chunk_size=256) 产出 256-token 块训练按语料原样，推理按代码原样。这是官方 checkpoint 自带的行为，不要"修正"
3Traditional 基线「先按句号切分，再累积到 256 token」fixed_size_chunking 是纯 token 滑窗截断，无句号切分以代码为准
4三个 backbone 各自初始化三个训练脚本都 from_pretrained('BAAI/bge-m3')不是 bug。论文 §4.2 自称「fixed 330M-parameter sentence-level encoder for all three」

#严重度问题修法
1🔴 阻断1_build_pretrain_datasets.py 把 part_* 存到 ./vector/jina-.../part_N，而 3_train_jina.py 读 ./vector/jina-.../train —— 路径不匹配，训练脚本直接报错加 P1.3 的合并步骤
2🔴 阻断baseline/traditional_chunking.py 的默认 tokenizer 硬编码 /share/home/ecnuzwx/UnifiedRAG/cache/models--Qwen--Qwen3-8B，服务器上不存在 → Sentenizer 初始化即失败。而它决定了句子切分粒度，直接影响所有结果显式传 tokenizer，或把默认值改成 Qwen/Qwen3-8B
3🔴 阻断HF 上 zai-org/LongBench-v2 只有一个 data.json（单 split），但脚本都 load_dataset(path, domain) 按 6 个 config 加载做 P1.1
4🔴 阻断src/ 没有 __init__.py；python "train and preprocess/3_train_jina.py" 时 sys.path[0] 是脚本目录不是仓库根 → from src.freechunker import ... 失败PYTHONPATH=. python ...
5🟠 高训练脚本输出 ./saved_models/jina-embeddings-v2-small-en/qwen3_epoch_{e}，测试脚本读 ../saved_models/2-epoch/jina-embeddings-v2-small-en/jina_epoch_1 —— 两边对不上统一路径
6🟠 高test_freechunker.py 里 dataset_path='../Data/LongBench-v2' 是相对路径，且与 EncoderQASystem 默认值 'zai-org/LongBench-v2' 不一致改成绝对路径
7🟠 高json_repair 未安装P0.4
8🟠 高单张 3090 跑 Qwen3-8B @ 40k 上下文吃紧（16.4GB 权重 + ~6GB KV）--tensor-parallel-size 2
9🟡 中超长 context 的显存风险：2M 词文档 → n≈10⁴ 句、m≈1.5n pattern，attention mask 到 GB 级监控峰值显存；必要时按 context 长度切块

4.1 执行中新增的坑 2026-10-03 实测

#严重度问题修法
14🔴 阻断语料本地加载方式：XiaSheng/FreeChunk-corpus 仓库布局里没有根 dataset_dict.json，所以 load_from_disk(根) 报 neither a Dataset directory nor a DatasetDict directory；而 load_dataset(根, split=...) 又会把 val/ 误判成 json split，报 Couldn't infer the same data file format for all splits。作者脚本能跑，是因为它在 hub 上加载而不是本地按 split 子目录逐个加载：load_from_disk(f"{root}/train")、load_from_disk(f"{root}/val")（并把脚本里 split="validation" 改成 split="val"）
15🟡 中hf-mirror 对 .DS_Store 返回 403，导致 snapshot_download 整个语料仓库失败（已下 2.7G 白下）ignore_patterns=[".DS_Store", "**/.DS_Store", ".gitattributes"]
实测确认：按 split 子目录加载后 train=100000 / val=9880，与官方 200,000 步（2 epoch × batch 1）完全吻合；[2,4] 的 span 数用 generate_shifted_matrix 复算与独立复算一致。
